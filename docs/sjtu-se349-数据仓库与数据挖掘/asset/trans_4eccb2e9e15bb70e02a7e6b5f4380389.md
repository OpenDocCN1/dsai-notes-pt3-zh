

## 多维数据模型 Cont.

例：AllElectronics 可能创建一个数据立方体 sales，以销售为中心的主题进行组织，使得数据能够在多维上进行建模和浏览。

- 维表：item（item_name, brand, type, ...），time（day, week, month, quarter, year, ...），...
- 事实：dollars_sold（销售额），units_sold（销售量）
- 事实表：包含度量和每个相关维表的码（item_key, time_key, ...）

![](img/6d25e92eb0bd56a22c311279c19b06b4_566_0.png)

- 数据仓库中，数据立方体是 n 维的。
- 以下是数据的 3-D 数据立方体表示。

![](img/6d25e92eb0bd56a22c311279c19b06b4_567_0.png)

4-D 情况下，观察起来比较麻烦，我们可以把 4-D 立方体看成 3-D 立方体的序列。

- 同理，把任意 n 维数据立方体显示成 (n-1) 维“立方体”的序列。

![](img/6d25e92eb0bd56a22c311279c19b06b4_567_1.png)

数据立方体只是对多维数据存储的一种比喻。

- 实际物理存储可以不同于逻辑表示。

- 在数据仓库的研究文献中，一个 n 维的数据立方体叫做**方体**。
- 给定一个维的集合，我们可以对每个可能的维子集产生一个**方体**。
- 根据这些方体，我们可以构造一个**方体的格**，每个方体都在不同的汇总级或不同的数据子集显示 group by 数据，方体的格称为**数据立方体**。
- 0 维方体存放最高层的汇总，称作**顶点方体**；而存放最低层汇总的方体则称为**基本方体**。

## 星型模式

- 注意，在星型模式中，每维只用一个表表示，而每个表包含一组属性。
- 这种限制可能会造成某些冗余——例如“Urbana”和“Chicago”都是美国伊利诺伊州的城市，在维表 location 中，这些城市实体的属性 province_or_state、country 会有冗余。

## 多维数据模型的模式

- 最流行的数据仓库概念模型是多维数据模型。这种模型可以以星型模式、雪花模式、或事实星座模式的形式存在。
- 星型模式（Star schema）：事实表在中心，周围连接着维表（每维一个），事实表含有大量数据，没有冗余。
- 雪花模式（Snowflake schema）：是星型模式的变种，其中某些维表是规范化的，因而把数据进一步分解到附加表中。结果，模式图形成类似于雪花的形状。
- 事实星座模式（Fact constellations）：多个事实表共享维表，这种模式可以看作星型模式集，因此称为星系模式（galaxy schema），或者事实星座（fact constellation）。

## 雪花模式示例

| 表 | 字段 |
|---|---|
| time | time_key, day, day_of_the_week, month, quarter, year |
| branch | branch_key, branch_name, branch_type |
| Sales 事实表 | time_key, item_key, branch_key, location_key, units_sold, dollars_sold, avg_sales |
| item | item_key, item_name, brand, type, supplier_key |
| supplier | supplier_key, supplier_type |
| location | location_key, street, city_key |
| city | city_key, city, state_or_province, country |

Measures（度量）：units_sold、dollars_sold、avg_sales。

## 雪花模式

- 规范化后的维表易于维护，并节省存储空间。
  - 与典型的巨大事实表相比，这种空间的节省可以忽略。
- 执行查询需要更多的连接操作，雪花结构可能降低浏览的效率。
  - 系统性能可能相对受到影响。

## 多维数据模型的模式 Cont.

- 在建立数据仓库时，数据仓库和数据集市之间是有区别的。
- 数据仓库收集了关于整个组织的主题（如顾客、商品、销售、资产和员工）信息，因此是企业范围的；通常使用事实星座模式，能对多个相关的主题建模。
- 数据集市是数据仓库的一个部门子集，针对选定的主题，因此是部门范围的；流行采用星型或雪花模式，适合对单个主题建模。

## 维：概念分层

- 一个概念分层（concept hierarchy）定义一个映射序列，将低层概念映射到更一般的高层概念。
  - E.g. 表示 location 的概念：杭州 → 浙江 → 中国 → 亚洲。
  - 概念分层允许我们在各种抽象级审查和处理数据。
- 概念分层可以由系统用户、领域专家、知识工程师人工提供，也可以根据数据分布的统计分析自动产生。

## 概念分层 Cont.

![](img/6d25e92eb0bd56a22c311279c19b06b4_578_0.png)

- 许多概念分层的定义隐含在数据库的模式中。
- 比如根据 location 维的属性，可以得到 street < city < province_or_state < country——这些属性按一个全序相关，形成一个层次结构。
- 维的属性也可以组成一个偏序，形成一个格。
- 形成数据库模式中属性的全序或偏序的概念分层称作模式分层。

![](img/6d25e92eb0bd56a22c311279c19b06b4_579_0.png)

- 概念分层为不同级别上的数据汇总提供了一个良好的基础。
- 综合概念分层和多维数据模型的潜力，可以对数据获得更深入的洞察力。
- 通过在多维数据模型中不同的维上定义概念分层，使得用户在不同的维上从不同的层次对数据进行观察成为可能。
- 多维数据模型（数据立方体）使得从不同的角度对数据进行观察成为可能。
- 概念分层则提供了从不同层次对数据进行观察的能力。
- 结合这两者的特征，可以在多维数据模型上定义各种 OLAP 操作，为用户从不同角度不同层次观察数据提供了灵活性。
