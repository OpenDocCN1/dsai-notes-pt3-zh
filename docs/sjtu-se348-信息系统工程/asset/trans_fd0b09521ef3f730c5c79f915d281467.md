## “信息工程”的完整方法论（1）

+   ①是企业模型（Enterprise or Business Model）的开发

这是其它所有构件都需要建筑于其上的基石。企业模型的开发在战略数据规划期间进行，力图确定企业的目标及为了达到这些目标所需要的信息

![](img/66d4369fd16c75b43d6800360af39d15_618_0.png)

## “信息工程”的完整方法论（2）

![](img/66d4369fd16c75b43d6800360af39d15_619_0.png)

+   ②是借助实体关系分析（Relationship Analysis）建立信息资源规划

+   这是自顶向下的数据类型分析，这些数据是必须被保存起来的，还要分析它们之间是如何联系的。

+   作实体关系分析，有时需要在整个企业范围内进行，有时只是搞某个部门、子公司、工厂，或者是企业的一部分。

“信息工程”这座大厦，如果没有底部的两块构件也可以建立起来，但是如果真的这样做，那就象在软土上建筑高楼大厦一样，没有坚固的基础。

## “信息工程”的完整方法论（3）

构件③是数据模型的建立（Data Modeling）

+   - 构件②实体分析全面地调查了整个组织所需要数据的类型。这样建立起的实体模型，虽然面广，但是没有包含实现数据库所需要的全部细节。
+   - 构件③把初步的实体模型划分成一些大组，它们有时被称为主题数据库，而这些就是详细模型。数据模型的建立工作产生出详细的数据库逻辑设计。
+   - 构件③是构件②的扩展，是使构件③达到更详细的程度，并且保证其稳定性。构件③使用了各种各样的检查手段。

## “信息工程”的完整方法论
构件①、②、③是基础和核心

## 关于构件①、②、③的说明

+   - 信息工程的一个重要认识是组织中存在的数据可以描述成与这些数据如何使用无关的形式。不能随意将一些数据项组成一个记录，这是因为数据具有一定的内在属性，根据它才能产生出稳定的数据结构。

+   - 通常数据模型的建立是在没有进行整个企业规划的情况下进行的。一些局部数据模型按特定的区域或特定的应用项目建立，这些局部模型容易建立和使用，而且还避免了各个部门之间的争论。但是，信息工程的目标是在整个企业中使数据的定义和结构取得一致，至少是那些必须共享的或用于整个控制系统中的数据应该在数据的定义和结构上保证完全一致。

+   - 全企业的实体分析如果没有高层领导的支持，就不能完成，这正是通常所缺少的。为了建立一个全面的计算机化的企业，有必要利用高层领导所制定的远景规划，并且实施底部几块构件的工作。信息工程的方法为高层领导提供了一个用于指导信息资源开发的行动计划。

## “信息工程”的完整方法论（4）-（5）

+   构件④⑤保证了信息中心和个人应用项目的迅速建立

有时，信息中心和个人的计算任务所使用的数据不是规范的，而且在详细的数据模型中没有进行描述，于是要进行的计算任务应建立在②之上，即它们所使用的数据不要进行详细的逻辑数据库设计、规范化和进行各种检查（如一致性、可靠性、完整性检查），这是构件⑤的内容

有时，用户需要使用详细的数据模型中的数据，来完成计算任务。这样用户就不必花费时间设计自己的数据，且有利于各独立开发的系统之间进行数据交换。这时，构件④面向终端用户的计算应建在第③块之上。

![](img/66d4369fd16c75b43d6800360af39d15_622_0.png)

## “信息工程”的完整方法论（6）

构件⑥是计算机化处理过程设计的基本工作

+   - 为了建立使用数据库的处理过程，需要用图形方法来表达数据的生成、检索、更新或删除等操作。
+   - 这些数据库作用图是容易建立的，但是还要把它们直接转换成第四代过程语言的编码图，这就成为构件④的基础了。

![](img/66d4369fd16c75b43d6800360af39d15_623_0.png)

## “信息工程”的完整方法论（7）-（9）

+   构件⑦分析人们将怎样使用数据

这对数据处理繁忙的系统是非常重要的。对于事务处理量少的应用程序系统，详细的数据使用分析是没有必要的。这些数据管理系统可以和最典型的数据库管理系统迥然不同。

+   构件⑧是数据分布的策略

研究分布式系统产生的若干原因和各种不同的分布形式，对数据模型进行划分，以便在各个独立的数据库中实现

+   构件⑨是物理数据库的设计

将数据模型和操作程序转换成为物理数据库的设计。对某些系统，完全规范化的数据隔离了清晰的数据结构，并会使检索复杂化。但是，如果这些系统是执行大型计算任务，这时性能成为优先考虑的因素，某些数据库管理系统DBMS对于这类系统是有利的。

![](img/66d4369fd16c75b43d6800360af39d15_624_0.png)

## “信息工程”的完整方法论（10）-（13）

+   □ 构件⑩、⑪是第四代语言和程序生成软件

+   ■ 用它们来建立计算机处理过程要比使用象COBOL或者PL/1这样的第三代语言快得多

+   ■ 在数据处理中这是非常重要的改进，它使用户不用设计他们自己的数据结构。在许多情况下，用户都非常希望自己能从数据处理的程序设计中得到解放。在数据被共享而不是私有的场合下，第四代语言的使用应当与数据模型联系起来。

+   □ 构件⑫表示在许多情况下，人们使用第四代语言来建立原型。这些原型可以在用户反复试用过程中，对它们进行多次的调整。

+   □ 构件（13）表示在某些情况下，一些由原型确定的处理过程可以使用第三代语言（通常是COBOL）来重新编程，这样可以适应具体机器的性能

## 信息工程 vs 软件工程

+   从软件工程的应用到信息工程的提出是一个微观到宏观、局部到全局、基层到顶层的发展过程，其发展驱动力是信息技术的快速发展和组织机构信息化应用的普及，以及由此引起的“数据危机”、“信息孤岛”

+   信息工程提出一整套“自顶向下规划和自底向上设计”的方法论，其中规划是基础、实施是手段，缺一不可

+   信息工程方法论的基础是企业模型、实体关系分析和数据模型的建立（即主题数据库规划）、数据分布规划三个模块

+   基于信息工程方法论的软件工程则是在信息工程顶层设计基础上，对信息系统开发过程通过采用良好的开发模型、设计方法、工程支持、过程管理方法，确保信息系统高效、高质量实施的方法和手段

| 比较点 | IRP需求分析 | 软件工程需求分析 |
|---|---|---|
| 参与人员 | 客户方一把手、高层业务领导、最终用户业务人员为主，技术人员参与，咨询人员辅助 | 技术人员为主，业务代表参与 |
| 前期工作 | IRP需求分析培训、统一熟识需求背景；资料采集 | 资料采集、应用系统需求界定 |
| 分析范围 | 组织机构全局或主要职能领域嗨 | 某个职能领域或某部门提出的某项业务信息化需求 |
| 分析内容 | 1、业务模型（职能域/业务过程/业务活动）<br>2、用户视图分析（用户视图/视图组成/视图元素拆分）<br>3、数据流分析（DFD1/DFD2，侧重职能间、业务过程间数据流向、内容、流量分析） | 1、需求获取：面谈、场景、原型、座谈会、观察<br>2、需求分析：检测需求冲突、求定需求边界、需求描述、需求分类、概念建模与细化<br>3、需求规格说明：系统定义、系统规格说明、软件规格说明 |
| 过程活动 | 指导、高层采访、分析研讨、结果录入、建模、评审 | 座谈、资料分析、文档编写、快速原型、评审 |
| 辅助工具 | IRP2000/Office | Rational Rose/RequisitePro/office/快速原型开发工具 |
| 分析结果 | 组织机构业务模型、数据元素表标准、用户视图标准、数据交换与分布设计、数据流图（一、二层） | 需求规格说明书、快速原型 |
| 侧重点 | 数据标准、数据分布与交换 | 需求界定、需求规格说明 |
